# Infinite Tower onboarding v2

Give new players a short route from their starter squad to a Floor 1 clear and a safe return. After that, recommend one useful action at a time based on what they own, what they have done, and where they are. Each objective should tell them why it matters, point to the correct location or control, and update when the game confirms the action.

## Branch implementation and rollout controls

- `Workspace.OnboardingV2 = false` keeps the legacy progression chain for profiles that have yet to select a guide version. Profiles keep their assigned version across sessions. The default selects v2.
- `Workspace.OnboardingMarkers = false` hides world and button cues independently of access and progression. Players can also hide the current marker or snooze the current lesson for 15 minutes. The Guide rail button opens the lesson reference and resumes snoozed hints.
- V2 retains the one-time legacy reward IDs for the corresponding confirmed actions. Synthesis and Promotion share the prior Pit reward. Getting a starter squad ready opens Tower access without a summon or a new deployment reward. Imported progress can satisfy lessons without granting rewards.
- Compare the `GuideCompleted` and `GuideTimeFromJoin` events by version and milestone. Use `GuideOffered` and `GuideSnoozed` to see which optional lessons players engage with. Creator Hub cohort measurements, synced first-run playtesting, and device checks are rollout tasks.

## What the current onboarding covers

The live code defines seven ordered goals: summon → deploy → clear Floor 1 → upgrade a weapon → assign a worker → use the Pit → buy a Fortress Tree node. Each step advances only while its event is active. Most of the steps also control access to another system. The Next Goal card shows a title, hint, step number, and reward. It has no target metadata or navigation action, and modal focus hides it at the point when the player may need instructions most. I confirmed the three onboarding modules are present in the open Studio place in Edit mode. The findings below come from repository code and were not measured in a fresh profile playtest. ## Proposed player journey

Use the starter squad to get players into the Tower quickly. Make the first summon an optional discovery goal available from spawn. Use the same server eligibility rules for the guide and the gameplay action, so a recommendation is always something the player can act on or has a clear path to make available.

| Moment | What the player sees | Completion or fallback |
| --- | --- | --- |
| Spawn and get ready | If a ready hero is already deployed, show the Tower entry. Otherwise highlight the Squad control, the open slot, and the eligible hero picker in sequence. | A ready deployed squad satisfies the step. If heroes are recovering, show the existing recovery information or a ready reserve. |
| Enter Floor 1 | Point to the Tower entrance or the existing HUD Tower entry, then highlight Floor 1 inside the selector. | Confirm the committed player visit to Floor 1. Distinguish visiting from assigning a squad to a floor remotely. |
| Clear Floor 1 | Use one prompt at a time for the first combat action, then direct the player to the actual boss encounter when it is available. Use the current input hints. | A server credited Floor 1 clear advances the goal. On wipe, switch to a recovery hint and resume from the same milestone. |
| Finish the first run | If the player has unbanked relic cargo, point to the nearest valid banking route and explain what is at risk. When travel is sealed, explain the boss lock. If there is no cargo, explain where to return safely and offer to continue climbing. | Track a safe return and a positive cargo bank as separate signals. Keep a first bank lesson available for the next time the player actually carries cargo. |
| Prepare for the next climb | In the hub, suggest the best available improvement. For example, equip an unequipped squad member, put a spare hero to work for Gold, or buy an affordable node. | A confirmed change satisfies that lesson. If the player keeps climbing, defer hub lessons until the next safe return. |

Priority in the guide should be safety or recovery, then the active first run milestone, then the best available discovery goal. Keep a compact Next Goal card with **Show me** and a way to dismiss or snooze hints. Context lessons can be resumed from a Help or Goals view. Dismissing a hint changes guidance preferences only. Copy should name the action and its benefit, for example “Assign a spare hero at the Guard Post to earn Gold while you’re away.”

## Feature lessons and where to attach them

| Feature | When to teach it | Guidance and success signal |
| --- | --- | --- |
| Hero summon and reveal | Optional at spawn or when the player wants a deeper roster and can afford a pull. | Point to the owned Summoning Altar, then the permanent banner and the chosen affordable pull. Teach the result screen after a successful summon. Keep limited banner and pity explanations inside their own UI. |
| Forge and equipment | First hub return with a ready hero and compatible gear. Show upgrading only when an eligible recipe is affordable. | Point to the Blacksmith, then the existing Forge workbench or equipment entry point, then the eligible control. Teach Equip Best where useful. For upgrades, show Gold and valid material availability, including equipped items that cannot be consumed. Use actual equip and upgrade commits as separate signals. |
| Guard Post and offline income | A spare eligible hero and an open worker slot, or the first offline earnings popup. | Guide through the plot exit to the Guard Post, then highlight the assignment control. Confirm a worker assignment. Explain offline earnings when the reward is shown. If the only ready hero is in the squad, wait or suggest a way to build the roster. |
| Upgrades and other facilities | The player can buy an eligible node or has just unlocked a building. | Highlight Upgrades and an affordable recommended node, then guide to the completed building if there is a free worker slot. Explain benefits in the relevant panels: Market boosts loot and extraction, Training Grounds boosts squad stats, and God’s Blessing improves summon luck. Respect facility construction and presence state. |
| Pit | A hero can benefit from Synthesis, or a capped hero qualifies for Promotion. | Point to The Pit, then the appropriate tab and preview. Explain donor consumption in the confirmation step. Teach Conversion and crafting when relevant inside the Pit, once they have UI. Credit each lesson only for its corresponding successful action. |
| Tower systems | On first cargo pickup, first safe zone, first wipe, or first encounter with a special mechanic. | Teach banking, sanctuary recovery, travel locks and the difference between squad commands and returning to the hub in their own contexts. Put Tower events and advanced floor mechanics in later prompts. |
| Raids | After exposure to tower combat, when the raid is accepting entrants and the player meets current requirements. | Offer an optional cue to the shared Raid Portal beside the Reflecting Pool. Inside, point out a signature telegraph, the Punish Window, and the results panel when each appears. If entry closes, drop the arrow and leave a reminder in the raid UI. |
| Other discovery | On opening the relevant panel or seeing a relevant reward. | Keep Artifact Summoning, inventory management, leaderboards, and PvP as contextual help. Keep their actions outside the core first run milestones. |

## Implementation sequence

### 1. Audit and establish the baseline

- Play a fresh profile through Floor 1 in a Rojo synced Studio test with a disposable save and development grants disabled. Record time to Floor 1, ambiguous copy, where players turn the wrong way, and first upgrade affordability. Verify the actual Tower entry, return, and banking routes and what the starter roster can do without spending Gems. Repeat with a profile that has no ready deployed hero.
- Instrument server milestones for profile ready, squad ready, first Floor 1 visit, first Floor 1 clear, first safe return, and first positive cargo bank. Use committed transactions and authoritative tower state for completion. Track optional lesson offers, completions and snoozes separately. Log broad reason codes for blocked recommendations, such as missing material or no eligible worker. Cap optional client feedback to known reason codes and apply rate limits.
- Compare fresh cohorts on time to first visit and clear, share reaching the first clear and a safe return, first bank among players who carried cargo, early wipes and departures, and D1 retention. Report first bank separately because some runs have no cargo. Start with a baseline before changing the order or gating. The repo has Tower telemetry but no onboarding funnel wiring was found in the source review. [Tower telemetry](../src/ServerScriptService/Combat/TowerTelemetry.luau)

### 2. Ship navigation and contextual UI on the existing flow

- Add stable guide target IDs to the onboarding config and extend the existing `OnboardingSync` read model with the active objective, hint key and ordered target candidates. Put a revision on the snapshot and seed it from initial profile bootstrap or an explicit read after the client listener is attached. Ignore duplicate or stale updates. Today, profile sync also pushes onboarding, and `Report` pushes it again after profile sync.
- Implement one local guide renderer near the React HUD. Reuse the current UI theme. World targets use an offscreen direction arrow when the next waypoint is outside view, a local marker when it is visible, and an outline on the facility near interaction range. Start with Summoning, Blacksmith, Guard Post, The Pit, and Tower entry. Use an owned plot lookup via `OwnerUserId`, facility attributes and the prompt anchor for position, and the visible model for the highlight. Map `ThePit` to the real building rather than the invisible Synthesis and Promotion compatibility models. Use explicit shared IDs for Tower and Raid destinations. For Guard Post, guide to the trail opening before the building when the wall separates the player from it. [Plot ownership](../src/ServerScriptService/Core/PlotManager.server.luau) · [Facility construction](../src/ServerScriptService/Core/FacilityPresence.luau)
- Let React and imperative controllers register and unregister visible controls by stable guide ID. While the matching menu is open, hand off to a ring and short hint on its next enabled button. Hide world guidance during unrelated modals, summon reveals and active combat. Preserve native input and gamepad focus. Show text as well as color, honor reduced motion, and position hints inside the safe area.
- Re-resolve on plot assignment, building rebuild or streaming, menu change, respawn and floor transition. When a target is missing or its prompt is disabled, use a valid waypoint or a text fallback until it is available. Clear the previous marker and connections on every handoff. Run camera projection only while a directional cue is visible. **Acceptance:** a player can find their own Blacksmith and Guard Post from any plot, follow the hint into the correct panel, and still interact normally on touch, keyboard, and gamepad.

### 3. Separate progress, lessons, and rewards

- Split `OnboardingService` responsibilities into server validated gameplay access and an independent lesson selector backed by stable IDs. Replace event strings with typed committed facts where context matters, including floor ID, facility ID, transaction kind and outcome. Reuse state that already proves a milestone, such as credited Floor 1 progress or a ready deployed squad. Store durable facts for first events that existing state cannot reconstruct. A late or repeated event should neither reset the guide nor duplicate a reward.
- Proposed access rules for the new cohort: a ready squad enables Tower entry, a credited Floor 1 clear opens Forge upgrades and the post-run fortress systems, and `MaxFloorReached` plus existing gameplay eligibility controls Floor 5 onward. Open the Pit with the post-run systems and let its normal eligibility rules determine available actions. Remove the legacy tutorial dependency from each corresponding server guard and its client lock copy in the same change. Keep plot ownership, travel safety, recipe costs, roster capacity, and raid eligibility server validated.
- Add a versioned migration after profile schema v5. Preserve every earned unlock and legacy reward claim. For a partially onboarded save, map proven milestones and infer Tower access from actual recorded progress. For finished players, start with context lessons only. Use immutable reward IDs and grant the reward with its claim in the same profile mutation. Treat legacy completed IDs as settled even if migration originally skipped them without paying. Define a per-cohort reward table before rollout, so auto-credit for existing state cannot mint extra currency and optional lessons cannot trigger a second legacy payout. Keep the old view readable during rollout and ensure the legacy cohort can still finish its chain. [Profile migrations](../src/ServerScriptService/Core/ProfileMigrations.luau) · [Current server gate and reward handling](../src/ServerScriptService/Core/OnboardingService.luau)
- **Acceptance:** a fresh profile can enter Floor 1 with its ready starter squad. A player can reach Floor 5 through normal clears without needing a Forge upgrade, worker assignment, or Pit donation. Returning and completed accounts keep access and can dismiss or replay relevant help without duplicate rewards.

### 4. Add post-run lessons and roll out in stages

- Ship Forge equipment and upgrade, Guard Post assignment, Upgrades, and first cargo banking first. They connect directly to the first repeatable run. Add facility unlock handoffs, Pit modes, Tower events and Raid guidance once the first set works. Assign each lesson an eligibility predicate, completion signal, fallback, and the screen or world target that owns it.
- Extend the progression tests with existing profile fixtures, replayed and out-of-order events, exact floor and transaction matching, persisted snoozes, and once-only rewards. Reuse the Forge, Pit, and tower extraction scenarios for integration. In Studio via Rojo and MCP, play fresh and migrated profiles across two different plots with multiple players, force delayed anchors and respawn, and check small touch screens and gamepad. Verify one visible cue at a time, correct target ownership, and successful transaction and state changes. Validate the place with `rojo build -o build.rbxl` before committing. [Progression tests](../tests/phase4-progression.luau) · [Tower extraction scenario](../tests/studio-tower-extraction.server.luau) · [Forge tests](../tests/forge-workbench.spec.luau) · [Pit tests](../tests/pit.spec.luau)
- Roll out navigation before the access changes so its effect is measurable. Then assign a stable test cohort for the shorter route and compare its first visit, clear and return rates with the baseline. Gate the guidance renderer separately from the access rules. If guidance needs to be disabled, preserve recorded milestones and granted access. Confirm that no fresh, returning, or low-resource profile is blocked before widening the rollout.
